# frontend

Интерфейс CQA: список диалогов, карточка, сравнение запусков, редактор чек-листа, апелляция, очередь проверки, отчёт. Контракт в [CONTRACTS.md](../CONTRACTS.md), типы в `src/api/types.ts` повторяют `ai/src/cqa_ai/contracts.py`.

Стек: Vite, React, TypeScript, Tailwind. Нужен Node 24.

## Запуск

```bash
cd frontend
npm install
```

Без backend, на синтетических данных:

```bash
npm run dev:mock
```

С backend на `http://localhost:8000`:

```bash
npm run dev
```

Браузер ходит на `/api`, Vite проксирует запросы на backend. Другой адрес задаётся так: `BACKEND_URL=http://localhost:9000 npm run dev`.

Откройте адрес, который напечатает Vite.

## Сборка и проверка

```bash
npm run typecheck    # проверка типов
npm run build        # рабочая сборка в dist/, без слоя моков
npm run build:mock   # статическая сборка с моками
npm run preview      # раздача dist/
```

Сборка статическая: относительные ассеты (`base: './'`) и `HashRouter`, поэтому её можно положить как HTML-компонент Dynamics 365.

## Настройка

| Что | Где |
|---|---|
| Адрес API | `apiBaseUrl` в `dist/config.js` меняется без пересборки. Запасной вариант `VITE_API_BASE_URL`, по умолчанию `/api` |
| Моки | `VITE_USE_MOCKS=true` при сборке или запуске |
| Хост | `src/host/hostAdapter.ts`. Компонент Dynamics может задать `window.__CQA_HOST__` до загрузки бандла |

Всё с префиксом `VITE_` и `config.js` попадают в браузер. URL организаторов, `audio_url` и ключи туда класть нельзя.

Если сборка раздаётся не через прокси, backend должен разрешить CORS для её адреса.

## Моки

Слой `src/mocks/` хранит состояние в памяти, перезагрузка страницы его сбрасывает. Диалоги выдуманы, реальных данных нет. В рабочую сборку слой не попадает.

| Диалог | Что показывает |
|---|---|
| `mock-ru-001` | N/A с перераспределением веса |
| `mock-ru-002` | Грубая ошибка при высоком итоге, повторяющиеся метки времени |
| `mock-kz-001` | Пропущенное действие: проверенный участок и ожидаемое место |
| `mock-en-001` | Флаг проверки и открытая апелляция |
| `mock-ru-003` | Результат провайдера-заглушки |
| `mock-ru-004` | Итог `null` и `partial_total` |
| `mock-en-002` | Запуск со сбоем, повторная оценка тоже падает |
| `mock-kz-002` | Диалог без оценки |
| `mock-call-001` | Условный звонок с кнопкой записи |
| `mock-web-001` | Канал без чек-листа: запуск «по каналу» даёт сбой с `checklist: null` |

Импорт по любому `group_id` добавляет ещё два диалога и показывает предупреждение. Новая оценка в моках всегда идёт через заглушку и сохраняет прежние ответы, если они подходят к версии чек-листа.

## Маршрут для проверки

1. Диалоги: фильтры, импорт, загрузка транскрипта, экспорт, выбор диалогов и запуск оценки.
2. Карточка `mock-kz-001`: клик по доказательству и «Показать в диалоге» у критерия «Завершение».
3. «Оспорить» у этого критерия, комментарий, сохранение.
4. Очередь проверки: изменить оценку с причиной.
5. Снова карточка: исходный и финальный итог рядом, решение у критерия.
6. Чек-листы: изменить критерий, сохранить новую версию, выбрать её при запуске оценки. Там же создаётся новый чек-лист, пустой или копией открытого.
7. Карточка с двумя запусками: «Сравнить запуски». Затем экран «Отчёт».

## Проверка с backend

```bash
cd backend
CQA_DB_PATH=/tmp/cqa-check.sqlite CQA_ALLOW_MOCK=1 uv run uvicorn cqa_backend.main:app --port 8000
```

Затем `npm run dev` в `frontend/`. Без `CQA_ALLOW_MOCK` и провайдера оценка завершается сбоем с текстом в поле `error`, так удобно смотреть экран сбойного запуска.
